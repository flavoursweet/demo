三分钟速读

这个项目让你选择一张遥感影像，点击识别或用文字提出任务，再查看滑坡候选区域、统计和报告。它调用你已经训练好的 U-Net 权重。

记住四个角色就够了：网页负责接收操作和显示结果；Python 后端负责组织任务；DeepSeek 负责理解文字、选择工具和解释结果；U-Net 负责计算图像中哪些像素属于滑坡候选区域。

三个按钮发送的是预设任务文字。当前仍由大模型判断该用哪种工具；按钮名称并没有直接锁定后端动作。因此“结果解读只读结果、识别流程只解释”是预期行为，需要通过实际执行记录确认。下一步可把快捷按钮改为明确指定动作，减少意图判断出错。

点击样本只会选图。拖动阈值当前只改变参数，尚未实现实时更新掩码。要得到新掩码，仍需提交识别任务。结果解读使用已有结果，不会自动按新阈值计算。

当前已有总候选像素、覆盖率、连通区域数量，以及输入有效地面分辨率后的面积估算。区域编号、逐区域面积表、阈值实时预览和两次结果对比属于后续计划。

汇报时分清三类评价：分割精度看掩码与真实标注的差异；工具选择是否正确看任务记录；回答是否可信看文字中的数字是否与真实统计一致。

## 1. 这个项目现在算什么

它是一个“面向滑坡语义分割的工具调用型智能体原型”。你把已经训练好的 U-Net 包装成可调用工具，让大模型理解用户任务、选择工具与参数，再根据真实执行结果回答。

本项目主要工作属于模型工具化与智能体应用开发。这里没有重新训练 U-Net，也不能把网页封装或接入大模型直接称为分割算法创新。

目前每轮选择一个动作，并执行预先编写的流程；尚未形成“模型观察中间结果、重新规划、连续调用多个工具”的自主循环。因此用“工具调用型智能体原型”介绍最准确。

| 能力 | 当前实现 | 应怎样理解 |
| --- | --- | --- |
| 任务理解 | 云端大模型选择工具和阈值 | 自然语言成为工具入口 |
| 真实执行 | 本机调用训练好的 U-Net | 分割结果来自计算，不是聊天生成图片 |
| 结果解读 | 云端结合真实统计回答问题 | 不同问题可以得到不同回答 |
| 上下文 | 当前页面保留最近最多4轮对话及当前结果编号 | 有限对话状态，不是长期记忆 |
| 工程闭环 | 网页、接口、队列、文件、日志、错误处理 | 从输入到可下载成果的完整应用 |
| 自主多步规划 | 未实现 | 不应宣称任意任务都能自动规划完成 |

## 2. 前端、后端、大模型和 U-Net 各干什么

| 部分 | 通俗解释 | 对应文件 | 输入 → 输出 |
| --- | --- | --- | --- |
| 前端 | 用户操作的工作台 | web/index.html、style.css、app.js | 文字、按钮、图片 → 请求；结果 → 页面 |
| 后端 | 接单并组织工作的程序 | server.py | 请求 → 任务状态、工具执行、成果地址 |
| 规划层 | 决定这次做什么 | agent.py | 当前问题、阈值、上下文 → 工具名和参数 |
| 推理工具 | 整理数据并调用分割模型 | engine.py | 图像路径、阈值 → 掩码和统计 |
| 分割网络 | 对像素进行分类计算 | models/unet.py + checkpoints/unet_best.pth | 图像张量 → logits |
| 回答层 | 针对具体问题解释结果 | responder.py | 问题、上下文、真实统计 → 自然语言回复 |

前端和后端是职责的区分，并不要求在两台电脑上。这里浏览器、Python 服务与 U-Net 都在本机，只有语言模型请求发送到云端。

后端使用 Python 标准库 http.server，前端使用原生 HTML/CSS/JavaScript。这个 Demo 没有使用 FastAPI、React 或 Vue。桌面上其他项目使用什么框架，不代表本项目也使用它们。

模型结构和权重也要分开：models/unet.py 定义网络怎样计算，unet_best.pth 保存训练后的参数。结构、权重和正确的输入处理需要配套使用。

## 3. 一张总图看懂当前调用关系

```text
浏览器：选择影像 + 输入文字 + 当前阈值 + 最近对话
                     │ HTTP / JSON
                     ▼
server.py：创建任务，放入队列
                     │
                     ▼
agent.plan() ── 第一次云端请求：选择工具和阈值
                     │
        校验唯一动作、参数类型和阈值范围
                     │
      ┌──────────────┼────────────────┐
      ▼              ▼                ▼
   segment        summarize          help
 engine.infer()   read_result()      准备问答上下文
   U-Net推理      读取已有统计       不执行分割
 保存图片/统计/报告
      └──────────────┼────────────────┘
                     ▼
responder.reply() ── 第二次云端请求：根据问题和真实结果回答
                     │
                     ▼
网页轮询任务 → 显示回答、图片、统计和下载链接
```

正常一轮云端交互通常有两次请求：第一次“决定做什么”，第二次“根据执行结果怎样回答”。若第一次规划格式不合规，会多一次 JSON 格式修复请求；这不是无限重试。

浏览器调用后端需要 HTTP；server.py 调用 engine.infer() 是同一 Python 程序里的函数调用。不要误以为每个 Python 文件之间都要再建网络接口。

## 4. 跟踪一次“识别当前影像并生成报告”

### 4.1 启动服务

双击“启动Demo.cmd”，start.ps1 选择 Python 环境，读取 .env 中的端口，启动 server.py 并等待健康检查，然后打开浏览器。若对应服务已经运行，会直接打开页面。

当前配置端口是8767，源码缺省端口仍是8765；访问时以配置和日志为准。127.0.0.1 表示本机。服务以后台进程运行，关闭浏览器不等于停止服务。

server.py 启动时调用 engine.load_model() 加载 U-Net 权重。模型保存在内存中供后续任务复用，不是每点一次按钮就重新加载一次权重。

### 4.2 网页加载样本

app.js 的 init() 调用 /api/health 和 /api/samples，取得服务信息、样本缩略图与路径。选中样本时只更新 selected 变量，没有执行推理。

### 4.3 点击按钮与聊天发送走同一条链

本轮已把单一入口改成“识别并报告”“结果解读”“识别流程”三个快捷按钮。按钮把各自预设的文字传给 submit()；聊天框发送也调用同一个函数，最终都提交到 POST /api/agent。三个入口的具体用途和完整链路见第17节。

下面是帮助理解的请求示例，不是新执行记录：

```json
{
  "message": "识别当前影像并生成报告",
  "threshold": 0.5,
  "gsd": "",
  "sample_id": "sample-01",
  "history": []
}
```

JSON 是前后端约定的信息结构。已有识别结果时还传 result_id；上传图片时传 image_base64 和 filename。Base64 是把图片二进制编码成文本，不是加密；传给本机后端后再解码为文件。

### 4.4 后端先返回任务编号

Handler.do_POST() 校验请求，生成任务编号，建立 JOBS 记录，交给线程池，返回 HTTP 202 和 id。202 表示已接受，不表示识别已经完成。

任务状态依次为 queued、running、done；出错时为 error。当前线程池 max_workers=1，任务串行执行。待处理与运行中的任务总数达到4时，会拒绝继续提交。

### 4.5 云端选择动作

run_job() 调用 agent.plan(message, threshold, has_result, history)。大模型接收工具定义、当前问题、阈值和近期对话，返回工具及参数。程序检查工具白名单、输出结构和阈值范围，才进入执行分支。

明确数字阈值也会先由程序提取；模型必须保留用户明确指定的数值。例如“阈值设为0.7”不能悄悄变成0.5。

### 4.6 本机执行分割

内置影像由 sample_id 查清单获得路径及真实标注；上传影像则解码保存。随后调用：

```python
stats = engine.infer(path, out, threshold, gt, gsd)
```

path 是输入路径，out 是输出目录，gt 是可选标注，gsd 是可选地面分辨率。infer() 保存图片并返回统计字典；server.py 再生成 JSON、CSV 和 Markdown 报告。

### 4.7 云端生成针对性回答

工具完成后，responder.reply() 收到当前问题、最近对话、实际工具名以及真实统计。它生成聊天回答，所以问“像素有多少”可以只回答像素数，问“IoU是什么意思”可以解释指标，不必重复完整功能介绍。

当前云端不会收到这条流程中的影像像素。规划阶段发送文字与状态；回答阶段还会发送结构化统计。因此应说“影像留在本机，任务文字、上下文与统计会发往云端”，不能说整个系统完全离线。

### 4.8 网页轮询并显示成果

submit() 大约每600毫秒查询 /api/jobs/<id>。renderSteps() 更新日志；任务完成后 renderResult() 显示图片和数字，message() 显示本轮回复。

结果JSON中的 files 保存图片URL。浏览器根据 /outputs/<id>/overlay.png 等路径再请求图片，而不是直接读取你的磁盘路径。

## 5. 接口可以理解为程序之间的“约定入口”

| 接口 | 用途 | 主要返回 |
| --- | --- | --- |
| GET /api/health | 查看服务状态 | 模型、设备、加载状态、模式标签 |
| GET /api/samples | 取得样本清单 | 样本编号、影像与标注地址 |
| POST /api/agent | 提交任务 | 202 和任务编号 |
| GET /api/jobs/<id> | 查询进度 | 状态、步骤、answer、result、planner、responder |
| GET /api/history | 查看已保存成果 | 最近至多30份识别结果 |
| GET /outputs/<id>/<文件名> | 显示或下载成果 | 图片、JSON、CSV、报告 |
| GET /、/app.js、/style.css | 加载网页 | HTML、脚本、样式 |

fetch() 发送 HTTP 请求；JSON.stringify() 把前端对象变成 JSON 文本；Python 的 json.loads() 把文本解析成字典。这就是前后端交换数据的主要连接点。

/api/agent 是你自己的应用接口；/chat/completions 是云端模型接口。它们不是同一个服务。健康检查成功仅能说明本机服务已起来，不能独立证明某一次云端请求成功，应看该任务的调用记录。

## 6. U-Net 如何把图片变成掩码

真正计算的位置在 engine.infer()：

```python
prob512 = torch.sigmoid(MODEL.infer(x))[0, 0].cpu().numpy()
```

MODEL.infer(x) 调用网络，sigmoid 把 logits 映射到0—1，[0,0] 取第一张图的单通道结果，cpu().numpy() 转成后处理使用的数组。

| 阶段 | 数据形状或数值 | 目的 |
| --- | --- | --- |
| 原图读取 | 宽W、高H，RGB | 纠正EXIF方向并统一通道 |
| 双线性缩放 | 512×512×3 | 固定模型输入尺寸 |
| 除以255 | 浮点0—1 | 缩放像素数值 |
| 通道归一化 | 减均值、除标准差 | 使用约定的输入处理 |
| 转置、增加批次维 | [1,3,512,512] | 适配PyTorch卷积 |
| U-Net输出 | [1,1,512,512] logits | 每像素一个前景分数 |
| sigmoid与取通道 | 512×512 | 获得概率形式的预测值 |
| 双线性恢复尺寸 | H×W | 对齐原图统计 |
| prob > threshold | H×W布尔掩码 | 判断候选前景 |

归一化均值为[0.485,0.456,0.406]，标准差为[0.229,0.224,0.225]。仅凭使用这组数值，不能推断网络使用了ImageNet预训练权重。

内置64×64样本放大到512×512再推理，不会获得新的真实遥感细节。非正方形图像当前也会直接缩为正方形，没有实现保比例填充或自动滑窗拼接。

load_model() 创建UNet、严格匹配加载权重、选择CUDA或CPU并调用eval()。eval()切换推理行为，inference_mode()减少不需要的梯度开销。当前流程没有损失计算、反向传播或优化器更新。

## 7. 网络结构怎么读

```text
输入：3通道，512×512
DoubleConv → 64通道，512×512
Down       → 128通道，256×256
Down       → 256通道，128×128
Down       → 512通道，64×64
Down       → 1024通道，32×32
Up + 跳跃连接 → 512通道，64×64
Up + 跳跃连接 → 256通道，128×128
Up + 跳跃连接 → 128通道，256×256
Up + 跳跃连接 → 64通道，512×512
1×1卷积 → 1通道logits
```

Down通过池化降低空间尺寸、提取更大范围信息。Up通过转置卷积恢复尺寸，再与编码器对应尺度的特征拼接。models/unet.py 中 torch.cat([x2,x1],dim=1) 就是跳跃连接的关键动作。

这是一项前景/背景二分类任务，但输出通道数为1：网络预测前景分数，阈值判断后取反即可表示背景。

调整阈值改变的是输出判定条件，不修改模型权重。当前每次改阈值重跑会重新执行推理，尚未缓存概率图来加速调参。

## 8. 三种工具与两次大模型请求

| 动作 | 本机执行内容 | 是否新运行U-Net | 云端最终回复 |
| --- | --- | --- | --- |
| segment | 预处理、推理、统计、保存成果 | 是 | 针对问题解释本轮真实结果 |
| summarize | 读取当前result_id对应文件 | 否 | 解释用户关心的统计或指标 |
| help | 准备功能/原理问答上下文 | 否 | 回答概念、流程、问候或追问 |

结果存在时，help回答也可以参考当前统计。询问“没有GSD能计算面积吗”既可能作为结果解释，也可能作为原理问答处理，关键是回答有依据且没有触发分割。

agent.summarize() 这个函数仍然存在，它负责生成确定性的统计摘要，供下载报告和备用显示使用；不要把它与“summarize工具最终聊天回复”混为一谈。现在最终聊天回复由 responder.reply() 生成。

执行日志中的 unet_segment、calculate_statistics、export_report 是固定分割流程里的步骤，不代表大模型自主选择了多次工具。两次云端请求也不等于多智能体协作：它们是同一个应用中的规划阶段和回答阶段。

## 9. 上下文、历史与文件保存

| 数据 | 保存在哪里 | 刷新或重启后的行为 |
| --- | --- | --- |
| 近期对话 | 前端conversation数组，最多8条消息即4轮 | 刷新、切换影像或清空结果时重置 |
| 当前影像与结果 | selected/upload/result变量 | 刷新后重新初始化 |
| 当前任务状态 | 后端JOBS内存字典 | 重启服务后消失 |
| 已完成分割成果 | outputs/<id>/ | 文件保留，可从历史记录读取 |
| 云端调用元信息 | logs/中的JSONL | 文件保留，用于追溯 |

历史消息只接收user/assistant角色，最多8条，每条截取最多2000字符。它是有限上下文，不是长期记忆，也没有知识库检索或跨会话记忆系统。

“总结刚才的结果”依赖result_id定位实际文件；模型并不是凭记忆猜测数值。恢复历史记录会清空当前输入选择，若要重新分割，需要重新选图。

每次分割产生：original.png、mask.png、overlay.png、probability.png、statistics.csv、report.md、result.json；有标注时增加ground_truth.png。

mask前景为255、背景为0；probability为16位PNG，除以65535可近似恢复预测值。report.md是固定模板报告，包含方法、来源、统计与图片引用，需与同目录图片一起保存才能显示插图。聊天回复的生成不会重写这份报告。

当前成果result.json是在生成聊天回复之前写入的，因此保存规划证据和分割步骤；回答阶段的responder信息在任务接口与logs/cloud_answers.jsonl中，不应声称完整聊天记录都保存在每个成果JSON里。

## 10. 错误处理与真实调用证据

### 工具调用格式不合规

第一次正常请求要求唯一函数调用。若模型只返回文字、返回多个工具、参数不符合约定，程序会再请求同一云端模型一次，改为返回{"tool":"help","threshold":0.5}这样的JSON结构。

第二次仍要检查工具名称、数值类型、阈值范围和明确数值的一致性。校验通过才执行；连续两次失败则报错。程序不会从随意文字里猜一个分割动作。明确拒绝、网络错误或HTTP错误并不都走这次格式重试。

### 文字回复生成失败

工具已经完成时，回答阶段失败不会丢掉分割成果。页面会明确标出回复失败，并提供固定摘要作为备用，不能把这段备用文字当成成功的大模型回答。

### 看哪些字段可以证明实际调用

- planner：规划模型、响应编号、工具、阈值、耗时。
- planner.attempts / recovered：是否发生格式修复重试。
- responder：回答模型、响应编号、耗时。
- logs/cloud_llm_calls.jsonl：成功规划调用记录。
- logs/cloud_answers.jsonl：成功回答调用记录。

模式名称只是标签；要证明某轮真实请求发生，应对照响应编号和任务日志。测试注入的模拟响应会单独标注，不作为真实云端推理结果。

## 11. 指标怎样解释才准确

候选像素数是掩码前景像素的个数；覆盖率=候选像素数/总像素数×100%。8邻域连通区域把横向、纵向和对角相邻的前景像素连起来，不能直接当作滑坡事件数。

若地面分辨率为g米/像素，代码估算面积=前景像素数×g²，前提是GSD正确且像素按正方形计算。没有GSD就没有平方米面积。当前TIFF读取也没有解析投影和地理坐标。

IoU、Dice等需要真实标注。设TP为正确预测的滑坡像素，FP为误报，FN为漏检：

```text
IoU       = TP / (TP + FP + FN)
Dice      = 2TP / (2TP + FP + FN)
Precision = TP / (TP + FP)
Recall    = TP / (TP + FN)
```

已有验收记录中，样本01在阈值0.5时得到878个候选像素，占4096像素的21.436%，IoU约79.34%，Dice约88.48%。这是单张样本记录，不是全数据集性能。

training_summary.json中的best_miou约80.47%、best_epoch=19属于归档训练指标，不能与单张样本前景IoU混用；详细统计口径要回到原训练代码核对。

上传影像没有配套标注时metrics为空，页面不显示IoU，仍可正常分割。同一概率图提高阈值会减少或保持候选像素，但IoU不一定提高。

## 15. 常见问题与下一步

**为什么不是普通网页套模型？** 目前有云端模型根据自然语言选择工具和参数，并使用真实执行结果回答；网页只是交互入口。这支持工具调用型智能体的定位，但不意味着已经实现复杂自主规划。

**大模型为什么要调用两次？** 规划时还没有本轮分割结果；工具完成后再把真实统计交给回答模型，才能生成有依据的解释。

**是不是有多个智能体？** 当前是一个应用的规划与回答两个阶段，没有实现多个独立智能体协作。

**能处理完整大幅遥感影像吗？** 当前上传上限10MB、最长边4096像素，统一缩放512×512。大幅影像需先切片，自动滑窗拼接与地理成果输出尚未实现。

**模型会记住以前所有对话吗？** 不会。仅有当前页面最近4轮消息和当前结果编号，刷新或换图会重置。

**下一步优先做什么？** 建立更全面的任务路由与回答质量测试集；增加大影像切片拼接、概率缓存及地理信息处理；若研究目标需要，再加入基于中间结果的多步规划。分割精度、工具选择准确率和回答事实一致性应分别评价。

## 17. 本轮前端改动与按钮背后的实现原理（2026-11-12）

### 17.1 页面上改了什么

本轮优化集中在前端交互和提示，没有重新训练 U-Net，也没有修改分割算法。

| 页面位置 | 改动 | 给使用者带来的变化 |
| --- | --- | --- |
| 左侧任务区 | 将原来的单一“开始智能识别”改为竖排的“识别并报告”“结果解读”“识别流程”三个按钮 | 用户能直接选择要做的事，不必先猜该怎么组织提示词 |
| 左侧下方 | 将识别成果下载区放到三个按钮下面 | 完成识别后，掩码、叠加图、报告等文件更容易找到 |
| 右侧助手区 | 扩大对话显示区域，将工具执行记录放在输入框下方 | 对话和执行步骤更醒目，记录不再挤在回答中间 |
| 结果与提示 | 关键统计数字加粗；增加未选影像、没有结果、服务或模型请求失败等提示；移除页面演示水印 | 数字更容易扫读，出错时能知道下一步该做什么 |

样本列表曾停在“正在读取…”。排查发现，旧脚本仍尝试给已移除的按钮绑定点击事件，按钮不存在时脚本报错，后续 init() 就没有执行。修复是删除这段过时绑定并更新脚本版本号。当前后端 /api/samples 接口已核对返回8个样本；浏览器里是否显示正常，仍以刷新后的页面实机确认。

补充：聊天区上移和放大是怎样实现的

这轮在 web/style.css 中调整了页面网格：右侧助手栏在普通桌面宽度下由约410像素扩大到最高480像素，宽屏下为500像素；主内容顶部间距缩小到10像素。对话区最小高度增加到340像素，宽屏下为380像素，消息字号调整到14像素，输入框最小高度增加到84像素。

CSS Grid 决定左、中、右三栏各占多少宽度；Flex 布局分配助手栏内对话、输入区和执行记录的空间；position: sticky 让右侧面板在页面滚动时尽量保持在顶部附近。它们改变显示方式，不参与模型推理。

需要注意：现有样式在窗口宽度不超过1100像素时仍把助手栏放到下一行，最小高度也可能让矮屏出现滚动。因此当前只能确认样式代码已调整，不能保证所有屏幕首屏都看得到输入框。后续应针对笔记本常用分辨率和浏览器缩放比例检查布局，必要时让窄屏的助手栏优先显示，并压缩或折叠执行记录。

### 17.2 三个按钮怎样触发程序

HTML 中每个按钮都带有一段预设任务文字，也就是 data-prompt。app.js 找到所有带 data-prompt 的按钮，并给每个按钮绑定同一类点击处理：把它的预设文字交给 submit()。所以按钮不会只把文字填进输入框，而是直接提交任务；在聊天框中手动输入相同内容，也会进入同一条提交流程。

| 按钮 | 发送给智能体的预设文字 | 前置条件与预期动作 |
| --- | --- | --- |
| 识别并报告 | 识别当前影像并生成报告 | 必须先选样本或上传影像；随后调用分割工具，执行 U-Net，显示掩码、统计和下载文件 |
| 结果解读 | 总结当前结果 | 必须已有识别结果；读取当前结果的真实统计来回答，不需要再运行 U-Net |
| 识别流程 | 请解释本次识别流程 | 走帮助/原理问答，不重新运行分割；没有影像也可以询问流程 |

submit() 会先检查按钮对应任务所需的条件。例如没有影像却请求识别，会在前端显示提示，不会把这个识别任务发给后端；没有识别结果却请求解读，也会提示先识别。条件满足后，前端将当前问题、最近对话、阈值、可选地面分辨率、样本编号或结果编号组成请求，发送到本机的 POST /api/agent。上传图片时，图片数据也会发给本机后端。

### 17.3 从点击到回答的底层流程

```text
点击按钮
  → 按钮携带的预设文字交给 submit()
  → 前端检查影像/结果是否具备，组装请求
  → POST /api/agent 提交到本机 Python 服务
  → agent.plan() 让云端 DeepSeek 选择 segment、summarize 或 help
  → 后端校验动作和参数，再执行对应的本机工具
  → 页面每约600毫秒查询一次任务状态并刷新执行记录
  → 完成后显示模型回答、识别结果、统计和下载链接
```

三个快捷按钮最终由同一个入口提交。当前由智能体判断文字意图，下面列出预期工具映射，并非按钮直接固定调用：

- 识别并报告 → segment：engine.infer() 预处理影像、复用已加载到内存中的 U-Net 执行推理、按阈值生成掩码并统计结果。
- 结果解读 → summarize：根据 result_id 读取已有结果与统计，交给回答层组织解释，不再计算新的掩码。
- 识别流程 → help：准备原理或流程问答上下文，由回答层解释处理步骤，不触发分割。

其中 DeepSeek 负责理解文字并选择任务、组织回答；本机 U-Net 负责图像像素计算。云端收到任务文字、有限对话上下文和结构化统计；图像分割在本机执行。

任务采用异步方式：后端先返回任务编号，前端再轮询任务状态。轮询过程中，renderSteps() 更新工具执行记录；识别完成时 renderResult() 更新图层、覆盖率、候选像素、区域数和下载链接；最后显示回答。

### 17.4 汇报时怎样描述这轮改动

可以说：“这次优化的是任务入口和操作反馈。我把原来单一的识别按钮拆成识别并报告、结果解读、识别流程三个明确入口。三个按钮都通过同一个任务提交函数进入智能体，智能体再按意图选择分割、总结或帮助工具。真正的掩码仍由本机已训练 U-Net 生成，因此这次前端优化改善了可用性和可解释性，不代表分割精度提升。”


## 18. 下一轮优化计划：功能、原理与验收目标

以下均为建议，本文更新不代表这些功能已开发完成。

第一优先：明确快捷按钮动作，并完善失败恢复。
当前按钮把文字交给大模型判断。可以增加明确的动作字段，让三个快捷按钮分别指定分割、解读和流程说明，自由聊天仍使用大模型规划。后端仍须校验动作、参数和是否有影像/结果。验收时重点看：解读和流程说明不产生新的 unet_segment 步骤，识别任务才产生新结果。
样本加载失败时可以提供“重新加载”按钮，分别提示本机服务、模型请求和影像读取方面的问题。验收时看服务恢复后能否重新加载样本并继续操作。

第二优先：阈值实时预览。
U-Net 先生成每个像素的概率，再用阈值决定保留哪些像素。当前每次重跑都会重新推理。可以缓存原始浮点概率数组，调整阈值时只重新生成掩码和统计，从而缩短等待。缓存必须绑定影像和模型版本；换图时不能误用旧概率。已有16位概率PNG是量化后的保存文件，若用于恢复，需考虑阈值边界附近的量化差异。
验收目标：同一影像调阈值时没有新增 U-Net 推理步骤；结果与相同概率数组直接阈值化一致；更换影像后不会沿用旧图结果。

第三优先：候选区域分析和结果对比。
已有的连通区域总数可进一步扩展为区域编号、大小排序和逐区域统计。小区域过滤是按像素数量去掉较小的预测块，可能减少噪声，也可能删掉真实小滑坡，需要展示过滤前后的结果。
面积估算已经有基础实现：若每个像素边长为g米，面积约为前景像素数乘g的平方。只有可靠GSD时才能报告平方米；图像宽高或放大倍数不能替代GSD。一个滑坡可能被分成多个预测块，所以连通区域数应叫“候选区域数”。
两次结果对比可先支持同一影像的不同阈值，并排展示掩码、覆盖率和区域数；有标注时再比较IoU和Dice。需要同时展示两次阈值，避免把不同参数的结果混淆。

持续开展：固定问题与实机验收。
准备几类固定问题：开始识别、调整阈值重跑、总结当前结果、询问流程、没有结果时要求解读、缺少GSD时询问面积、对上轮回答继续追问。分别记录工具选择是否正确、数字是否与统计一致、失败提示是否可操作，不能把这些混成一个“模型准确率”。
页面验收还应覆盖样本加载、输入框首屏可见性、长回答滚动、窄屏布局和重复点击。历史测试通过记录不能替代新版本验收。

建议一周安排：先做好按钮任务与异常恢复，再完成阈值预览，最后用固定问题清单记录改进结果。区域级分析和多参数对比可作为下一阶段工作。
